# Chronodrom — Claude Code Guide

## Project

iOS running tracker app. Reads workouts from Apple HealthKit, lets user classify runs by type, filter and compare. Built with Expo (React Native) on Windows via EAS cloud builds.

## Key Files

- `docs/HANDOFF.md` — **read at session start**: current task status, open bugs, decisions from previous sessions.
- `architecture.md` — tech stack, file structure, data model, phase roadmap. Keep updated when architectural decisions change.
- `FRONTEND_SPEC.md` — pixel-level UI spec (colors, typography, layouts, component styles). Source of truth for all visual decisions.
- `docs/superpowers/specs/2026-08-07-surge-implementation-design.md` — full design doc with all phase decisions and rationale.

## Stack (Phase 1)

- **expo-router** — file-based navigation. Screens live in `app/`. Tabs in `app/(tabs)/`.
- **Zustand** — global state. Stores in `src/store/`. One store per domain (runs, run types, profile, auth).
- **expo-sqlite** — offline copy + outbox. Schema, queries and sync in `src/db/` (self-check: `node src/db/sync.check.ts`). Profiles sync too (`user_id` in the cloud ↔ `id` locally).
- **Supabase** — auth + cloud Postgres. Client and all calls in `src/api/` only; screens/stores import from `src/api/auth.ts`, never `@supabase/supabase-js`. Keys in `.env` (local) and EAS env (builds).
- **@kingstinct/react-native-healthkit** (v16, Nitro) — reads HealthKit workouts. Logic in `src/healthkit/`; the module is lazy-loaded via `src/healthkit/native.ts` (Expo Go has none — never import it at top level). Self-check: `node src/healthkit/import.check.ts`. See `architecture.md` → HealthKit import.
- **react-native-svg** — SVG area/line charts. Shared `Chart` component in `src/components/`.
- **Insights (RA-29)** — `src/insights/` is pure (metric catalogue, summary maths; self-check `node src/insights/summary.check.ts`); the HealthKit reader is `src/healthkit/insights.ts`, in-memory cache in `useInsightsStore`.
- **Shoes (RA-8)** — `src/shoes/` pure (self-check `node src/shoes/shoes.check.ts`); catalogue in Supabase (`shoe_brands` / `shoe_models`), seed generated by `node scripts/gen-shoe-catalogue.mjs` from the spec appendix; logos in the public bucket `brand-logos` by brand-name file. Shoe distance is never stored. See `architecture.md` → Shoes.

## Development Workflow

- **Expo Go**: use for all UI work with mock data. Works on Windows → iPhone without any build step.
- **EAS dev build**: installed on Bar's iPhone (2026-11-18). Required for HealthKit and native Google/Apple sign-in. Run with `npx expo start --dev-client`. Rebuild (`eas build --profile development --platform ios`) only after adding native packages or changing `app.json`.
- **Auth email links**: Supabase rejects redirect addresses with an IP host, so in Expo Go use `npx expo start --tunnel` (`exps://`); the dev build uses `chronodrom://`. See `architecture.md` → Development Workflow.
- After switching branches, run `npm install` (branches have different dependencies).
- **EAS production**: `eas build --profile production --platform ios` → TestFlight.

## Data Rules

- HealthKit is **read-only**. Never write back to it.
- Supabase Postgres is the source of truth (`supabase/schema.sql`). SQLite is the phone's offline copy of runs + run types plus the outbox (`pending_ops`). Every user change goes through `writeChange` in `src/db/queries.ts`, then `syncNow()` — see `architecture.md` → Sync.
- Manual edits live in `runs.edits` on top of HealthKit data; HealthKit sync must never overwrite them, nor `type_id` / `needs_type` / `notes` / `shoe_id` (tripwire in `src/db/sync.check.ts`). The default shoe of a run type only fills a run that has no shoe.
- Run types: every change goes through `useRunStore.setType(ids, typeId)` (clears `needs_type`); the picker is `pickRunType()` in `src/components/RunPickerList.tsx`. Runs that started after the account was created import with `needs_type = true` (`needsType()` in `src/healthkit/mapWorkout.ts`) → Dashboard New run card. See `architecture.md` → Run types.
- Deduplication: Apple Health runs use the HealthKit workout UUID as `runs.id`; imports use `writeChange('runs', 'insert', …)`, which inserts only if missing. The same run copied into Health by another app (overlapping time) is skipped; the Apple Watch copy wins (`src/healthkit/dedupe.ts`).
- Cloud schema changes: update `supabase/schema.sql` and add a one-off script in `supabase/migrations/` for the existing DB (Bar runs it in the Supabase SQL Editor).
- `typeId` is nullable — null means unclassified.

## Conventions

- All monetary/distance/pace display respects `user.unit` ('km' | 'mi') (screens hardcode `'km'` until RA-6 adds the setting; the cloud `profiles.unit` column exists).
- Pace display: `fmtPace(secPerKm)` from `src/utils/format.ts`.
- Charts draw real stored data only, never generated series. The HR chart = `run.hrCurve` (80 × [min, max] bpm, built at import); no curve → no HR chart.
- Run type colors: `oklch(0.66 0.17 <hue>)` where hue comes from `RunType.hue`.
- HR zones: zone starts always come from `useZoneStarts()` (`src/store/useProfileStore.ts`); time-in-zone = `zoneTimes(run.hrHist, starts)` from `src/utils/zones.ts` (self-check `node src/utils/zones.check.ts`). Runs store an HR histogram, never zone totals. HRmax always via `effectiveHrMax(profile, runs, today)` (`node src/utils/profile.check.ts`); never a hardcoded HRmax.
- Insights read Apple Health live — never store Health metrics (only the hide/order layout in `profiles.insights_layout`). Group colours come from `groupColors` in `src/utils/tokens.ts`; lime is reserved for insight cards.

## Git

Never run any git commands (git add, git commit, git push, git checkout, etc.). Bar handles all git operations himself. When files are ready to commit, say so and list what changed.

When Bar says the work is ready to commit, write out the git commands for him to run, in order and one per code block. Split the changes into several commits by subject (data/schema, logic, screens, docs…), never one big commit. For each commit, write `git add` with its files and then `git commit` with a message. Commit messages never get a `Co-Authored-By` line or any other AI attribution (also not in PR descriptions). Then push. Never tell him to merge into `main` locally: branches reach `main` through a GitHub PR. Don't run them yourself.

## Branch-per-task rule

Every task is done on its own branch. At the start of every session and every new task:
1. Read `.git/HEAD` to check the current branch (file read, not a git command)
2. If on `main` or on the wrong branch for the current task, stop and tell Bar which branch to create or switch to before writing any code
3. Branch names follow the pattern: `feature/<short-task-name>` (e.g. `feature/mock-data`, `feature/app-shell`, `feature/dashboard`)
4. Never write code until the branch check passes
5. Rename the Claude session to the branch name (e.g. `feature/healthkit`) so Bar can find it again later
